# Правила ревью Go-кода

Применяй эти правила при запросе `review`. Учитывай намерение изменения и версию Go из `go.mod`. Сообщай о проблемах, которые влияют на корректность, надёжность или поддержку кода; личные предпочтения по стилю не выдавай за ошибки.

## Правила проверки

1. **Проверка типа ошибки.** Для поиска ошибки определённого типа в цепочке предпочитай `errors.AsType[T](err)` вместо `errors.As(err, &target)`: запись короче и не требует переменной-приёмника. Это правило применимо, когда версия модуля — Go 1.26 или новее и `T` реализует `error`. Выбирай точный тип `T` (`MyError` или `*MyError`) в соответствии с тем, что возвращает код. Для сравнения с конкретной ошибкой-значением используй `errors.Is`, а не `AsType`.
2. **Сохранение причины ошибки.** При добавлении контекста используй `%w`; пользовательские обёртки должны предоставлять `Unwrap()`. Проверяй, что нужный тип ошибки доходит до слоя, который принимает решение, например до HTTP-обработчика. Не выбирай поведение по тексту `err.Error()`.
3. **Разные исходы запроса.** Отличай отсутствие результата от ошибки базы или сети. Для `pgx.QueryRow(...).Scan(...)` отсутствие строки определяется через `errors.Is(err, pgx.ErrNoRows)`; SQLSTATE из `*pgconn.PgError` относится к ошибке, возвращённой PostgreSQL. Проверяй, что ожидаемое отсутствие ресурса даёт 404, а неожиданная ошибка — 500, без раскрытия внутренних деталей клиенту.
4. **Контекст запроса.** Передавай `context.Context` от HTTP-запроса через сервис к операциям БД и внешним вызовам. Проверяй обработку отмены и тайм-аутов; `context.Background()` внутри операции, зависящей от запроса, требует обоснования.
5. **Ресурсы и конкурентность.** Проверяй закрытие `Rows`, файлов и других ресурсов, возврат соединений в пул, завершение горутин и отсутствие гонок. `go test -race` запускай, когда изменение затрагивает параллельное выполнение и такой запуск доступен.
6. **HTTP-контракт.** Сверяй маршруты, методы, параметры, статусы, заголовки и формат тела ответа с OpenAPI-спецификацией и фактическим поведением. Не считай ответ `200` признаком успеха, если операция фактически не выполнена.
7. **Тесты по поведению.** Для изменённой логики проверяй успешный исход, ожидаемую ошибку и неожиданную ошибку, если они влияют на результат. Тест должен падать при нарушении контракта, а сообщение об ошибке должно показывать полученное и ожидаемое значения. Однотипные проверки с разными входными данными или ожидаемыми результатами оформляй табличными тестами. Тесты API помещай рядом с API, тесты репозитория — рядом с репозиторием. Для выборочного запуска через `go test -run` используй общий префикс имени тестовой группы.
8. **Имена функций.** Называй функции в стиле lowerCamelCase или UpperCamelCase в зависимости от видимости. Для тестов используй `Test` и UpperCamelCase для имени группы и сценария, разделяя их одним подчёркиванием: например, `TestPostgresRepository_ConvertError` и `TestPostgresRepository_CollisionLimit`. Внутри частей имени не разделяй слова подчёркиваниями.
9. **Сгенерированный код.** При изменении API сначала проверяй исходную OpenAPI-спецификацию и команду генерации. Не предлагай ручные правки в `gen/`, которые исчезнут при следующей генерации.
10. **Форматирование и проверка.** Проверяй `gofmt`, `go test ./...` и относящиеся к изменению предупреждения `go vet`. Указывай, что удалось запустить, а что проверить не удалось; не выдавай успешную компиляцию за полную проверку поведения.

## Как представить результат

- Сначала перечисли найденные проблемы по убыванию важности. Для каждой укажи файл и строку, конкретный сценарий и последствие.
- Затем кратко укажи оставшиеся пробелы в проверке и результат выполненных команд.
- Если существенных проблем нет, напиши это прямо. При запросе `review` ограничься анализом и не меняй код без отдельной просьбы пользователя.
